## 1. 内容设计原则

### 1.1 首要原则：笛卡尔积中绝大多数组合必须合理【已确认】

一台老虎机有 N 列，每列各取 1 项，**任意组合都应该能读通、能执行**。实现方式：

| 手段 | 做法 |
|---|---|
| 列之间互相独立 | 每一列回答一个独立的问题，不依赖其他列的取值 |
| 每列内部写法统一 | 同一列的候选项使用同一种语法角色，保证都能填进结果句式 |
| 规避“半依赖”维度 | 例如做菜不用“做法”列（炖、炸、凉拌会和食材冲突），而用“风味”列 |
| 模糊处理先后顺序 | 约会的句式用“+”连接，不写“先…再…”，避免时间顺序冲突 |
| 列表互不重叠 | 调酒的“饮料”和“再加一种”两列选项不重复，避免“雪碧兑雪碧” |
| 组合抽查 | 每个模板都要做枚举检查和随机抽样人工审核（见 §9） |

**合格线**【建议】：随机抽样 50 个组合，**明显荒谬或无法执行的 ≤ 2 个**，“有点奇怪但能做”的 ≤ 5 个。

### 1.2 其他原则

1. **随机列只放用户无所谓的维度**【已确认】：预算、距离、强度不做成列。
2. **标签自己说清楚**【已确认】：候选项只有 `label`，**不配说明文字**。看不懂的选项要改写，而不是加注释；必要的通用说明放进模板级的 `note`（结果提示）或 `notice`（首次须知）。
3. **标签长度**：`label` ≤ 6 个汉字为佳，硬上限 8；超过 6 字的在自动检查中给出警告。
4. **有趣，不尬**：聚会、情侣场景以“好玩、烘托气氛”为第一标准，宁可删掉也不放让人尴尬的内容。
5. **PG-13 上限**【已确认】，安全红线见 §10。
6. **避免博彩元素**：文案中不出现“中奖、下注、Jackpot、手气”等词。
7. **语气**：轻松、口语化，像朋友提建议；避免说教。

## 3. 数据字段约定

字段的类型定义见 TECH_DESIGN，这里只说明内容层面的含义。

### 3.1 候选项字段

| 字段 | 说明 |
|---|---|
| `id` | 稳定 ID，格式 `{模板ID}.{列ID}.{两位序号}`，例如 `cook.main.01`。**一旦发布，永不修改、永不复用**；删除候选项时留空号 |
| `label` | 唯一的展示文字，滚轮和结果卡片都用它 |
| `intensity` | 1–3，仅 `couple` 使用；不填视为 1 |
| `tags` | 内容分组标签：`touch`、`privacy`、`outside`、`alcohol`（V0.1 仅 `party` 使用） |
| `weight` | 权重，默认 1；只在预设中使用（V0.1 仅 `party` 的“全体一起”为 0.5） |

**不设 `detail` 字段**【已确认】。

### 3.2 模板 / 列字段

| 字段 | 层级 | 说明 |
|---|---|---|
| `sentence` | 模板 | 结果句式，`{列ID}` 为占位 |
| `sentenceSuffix` | 可选列 | 可选列开启时追加到句式末尾 |
| `note` | 模板 | 结果卡片底部的一行固定提示，≤ 40 字，可选 |
| `notice` | 模板 | 第一次进入时的须知，≤ 60 字，可选 |
| `tagGroups` | 模板 | 内容分组：名称、对应 tag、是否默认整组排除（PRD F22） |

## 4. 今天做什么菜（`cook`）

### 4.1 场景定义

- **用户**：在家做饭的人，买菜前或打开冰箱时不知道做什么。【已确认】
- **定位**：V0.1 帮用户**决定今天用什么食材**，转出来的结果就是今天的采购清单；具体菜谱由用户自己搜索。【已确认】
- **列**：主料 × 配菜 × 风味（方案 B）【已确认】
- **为什么用“风味”而不是“做法”**：风味几乎可以搭配任何食材；做法（炖、炸、凉拌）则经常与食材冲突，例如“生菜 × 炖”“牛腩 × 凉拌”。

### 4.2 句式与提示

```
sentence: 今天用{main}配{side}，做一道{flavor}味的菜
```

示例：今天用**鸡腿**配**西兰花**，做一道**咖喱**味的菜

结果卡片底部固定显示一行轻提示：“AI 推荐菜谱即将上线”，不带按钮（PRD F17）【已确认】。不设 `note`。

### 4.3 候选项

|---|---|---|---|
| 01 | 鸡腿 | 西兰花 | 番茄 |
| 02 | 鸡胸肉 | 土豆 | 咖喱 |
| 03 | 五花肉 | 青椒 | 蒜香 |
| 04 | 里脊肉 | 洋葱 | 黑椒 |
| 05 | 排骨 | 包菜 | 麻辣 |
| 06 | 牛肉 | 茄子 | 酸辣 |
| 07 | 肥牛片 | 蘑菇 | 照烧 |
| 08 | 羊肉 | 胡萝卜 | 葱油 |
| 09 | 虾仁 | 玉米 | 鱼香 |
| 10 | 鱼片 | 西葫芦 | 红烧 |
| 11 | 鸡蛋 | 莲藕 | 孜然 |

| 13 | 午餐肉 | 金针菇 | — |

**内容取舍：**
- 配菜不放番茄（与风味“番茄”重复），不放生菜、豆芽（与红烧、咖喱等风味搭配别扭）。
- 配菜不放四季豆：没有说明字段后，无法提示“必须彻底炒熟”，存在食品安全风险，改为玉米。

### 4.4 组合检查结论

- 主料 × 风味（156 对）、配菜 × 风味（156 对）已逐一检查，均可做出一道家常菜。
- 已知的弱组合（可接受）：排骨 × 金针菇 / 西葫芦（熟的时间相差大）、午餐肉 × 红烧、鸡蛋 × 照烧、鱼片 × 孜然。
- 不需要互斥规则。

## 6. 聚会挑战（`party`）

### 6.1 场景定义【已确认 D24】

- **用户**：**熟人局**——老朋友、室友、同学，3–8 人，一台手机放在桌子中间或传着玩。
- **标准**：**有趣、能烘托气氛**是第一标准；不尬、不冒犯。
- **允许**：不过分的身体接触、真心话和不太冒犯的隐私、联系场外的人或发布内容。
- **控制方式**：敏感内容打上分组标签，可以整组排除（PRD F22）；任何挑战都可以“换一个”。
- **玩法**：game，按轮进行。
- **列**：谁来 × 做什么 × 附加条件。第 3 列从“怎么做”（只和声音有关）改为**类型多样的附加条件**；经检查能找到足够多与所有任务兼容的条件，因此保留第 3 列。

### 6.2 句式

```
sentence: {who}：{task}（{rule}）
note:     左右、对面都以拿手机的人为准
```

示例：**左手边的人**：**打给通讯录第8人**（**全程不许笑**）

### 6.3 内容分组

| 分组名称 | tag | 范围 | 默认 |
|---|---|---|---|
| 身体接触 | `touch` | 拥抱、牵手、捏肩、贴脸、掰手腕、喂食、弹脑门这一级别 | 开启 |
| 隐私话题 | `privacy` | 真心话、感情经历、相册、屏幕使用时间这一级别 | 开启 |
| 场外互动 | `outside` | 给场外的人打电话或发消息、发朋友圈、改签名【已确认】 | 开启 |
| 饮酒 | `alcohol` | 喝一口 | **整组排除**【已确认】 |

所有分组都关闭时：“做什么”剩 6 项，“附加条件”剩 7 项，满足每列 ≥ 3 项。

### 6.4 列间兼容性规则（写内容时必须遵守）

- “谁来”使用相对描述【已确认 D9】，在任何一桌人中都能找到对应的人；方位以拿手机的人为准（写在 `note` 中，不写进标签）。
- “做什么”中需要搭档的任务一律写成“在场一人 / 找人”，由执行者自己挑，避免和“谁来”冲突（例如不能写“抱右边的人”，否则会出现“右手边的人：抱右边的人”）。
- “附加条件”必须与**所有**“做什么”兼容，只用以下类型：时间、协作、评判、表情、奖励、豁免、站位、惩罚、特权、饮酒。不用声音类条件（会和不说话的任务冲突），不用“闭眼”（会和看手机的任务冲突），不用“做两遍”（会和具体的问答任务冲突）。

## 7. 便利店调酒（`mix`）

### 7.1 场景定义【已确认 D22】

- **用户**：成年人，聚会前或宿舍、出租屋里想喝点不一样的，材料全部在便利店买。
- **结构**：默认 1 种酒 + 1 种饮料；用户可以打开“再加一种”，变为 1 种酒 + 2 种饮料【已确认】。
- **列**：基酒 × 饮料，可选列“再加一种”**默认关闭**【已确认】。
- **玩法**：decision，重转次数默认不限。
- **内容约束**：不出现任何酒或饮料品牌；不放能量饮料（酒精 + 咖啡因有健康风险）；“饮料”和“再加一种”两列的选项互不重复。

### 7.2 句式、提示与须知

```
sentence:       用{base}兑{mixer}
sentenceSuffix: ，再加点{extra}          （“再加一种”开启时追加）
note:           酒 1 份、饮料 3–4 份，多加冰，适量就好
notice:         未成年人请勿饮酒，喝酒不开车。
```

示例：
- 默认：用**金酒**兑**汤力水**
- 打开“再加一种”：用**金酒**兑**汤力水**，再加点**西柚汁**

### 7.3 候选项

| # | 基酒（`base`） | 饮料（`mixer`） | 再加一种（`extra`，可选列） |
|---|---|---|---|
| 01 | 伏特加 | 雪碧 | 橙汁 |
| 02 | 金酒 | 可乐 | 桃汁 |
| 03 | 朗姆酒 | 苏打水 | 葡萄汁 |
| 04 | 威士忌 | 汤力水 | 苹果汁 |
| 05 | 白酒 | 乌龙茶 | 西柚汁 |
| 06 | 梅酒 | 绿茶 | 乳酸菌饮料 |
| 07 | — | 冰红茶 | — |
| 08 | — | 柠檬茶 | — |

**分列思路**：“饮料”放气泡水和茶饮（打底），“再加一种”放果汁和乳酸菌饮料（调味）。打底 + 调味的结构保证两种饮料基本都能搭配。

**刻意不放的**：啤酒（兑苏打水、汤力水、乌龙茶都别扭）、椰汁（和可乐、汤力水、柠檬茶冲突）、能量饮料（健康风险）。

### 7.4 组合检查结论

- 基酒 × 饮料（48 对）已逐一检查，均为常见或可接受的兑法。
- 饮料 × 再加一种（48 对）已逐一检查。已知的弱组合（可接受）：可乐 × 乳酸菌饮料 / 西柚汁、汤力水 × 乳酸菌饮料、冰红茶 × 葡萄汁、白酒 × 乳酸菌饮料。
- 不需要互斥规则。

## 8. 情侣互动（`couple`）

### 8.1 场景定义

- **用户**：情侣，两人在家，用一台手机。
- **玩法**：game，按轮进行；“换一个”永远可用、不计次数。【已确认】
- **列**：谁主动 × 在哪 × 做什么，可选列“附加规则”（默认关闭【已确认】）。
- **两个主体**【已确认】：所有互动都发生在两人之间，句式写成“**主动的一方** + **对方**”。单向动作在标签里直接写“对方”（例如“公主抱对方”）；双向动作不写对象（例如“对视一分钟”）。
- **尺度**：温和（1）/ 心动（2）/ 升温（3），默认“温和”【已确认】。
- **内容上限**：PG-13【已确认】。亲吻、拥抱、公主抱、坐腿上可以；任何涉及脱衣、性行为、隐私部位的内容都不可以。

### 8.2 句式与须知

```
sentence:       {who}主动，在{place}{action}
sentenceSuffix: ，附加规则：{rule}       （“附加规则”开启时追加）
notice:         互动需要双方都愿意，不想做随时点“换一个”。“你”指拿着手机的人；抱起对方时注意安全。
```

示例：
- **你**主动，在**沙发上****公主抱对方**
- **猜拳输的**主动，在**窗边****对视一分钟**，附加规则：**全程不许笑**
- **两人轮流**主动，在**厨房****喂对方一口**

### 8.3 列间兼容性规则（写内容时必须遵守）

- “谁主动”的每一项都能读成“X 主动”；“两人轮流”= 两人轮流各主动一次，因此单向动作也能搭配。
- “在哪”只放**家中的普通位置**，不放浴室、被窝等容易越过尺度的地点；只有“床边”标为 2 级。
- “做什么”不放依赖特定地点的动作（例如壁咚需要墙，在沙发上、地毯上做不了）。
- 抱起类动作（公主抱、背着走）允许【已确认】，安全提醒放在 `notice` 中。
- “附加规则”必须与**所有**“做什么”兼容。已经剔除的例子：“闭着眼睛”（与“对视一分钟”冲突）、“看着对方眼睛”（与“从背后抱住”冲突）。

## 9. 内容质量检查流程

预设内容在发布前、以及每次修改后，都要完成以下检查。

### 9.1 自动检查（开发时写成脚本或单元测试）

| 检查项 | 规则 |
|---|---|
| 标签长度 | 所有 `label` ≤ 8 字；> 6 字时输出警告 |
| 列内唯一 | 同一列中 `label` 不重复 |
| 列间不重叠 | `mix` 的 `mixer` 与 `extra` 没有相同的 `label` |
| ID 唯一稳定 | 所有 `id` 全局唯一，符合命名格式；与上一版本相比没有被修改或复用 |
| 句式占位 | `sentence` 中的每个占位都对应一个存在的列 ID；每个非可选列都出现在句式中；可选列只出现在 `sentenceSuffix` 中 |
| 尺度覆盖 | 有尺度的模板，在每一档下每列至少 3 个可用项（PRD E05） |
| 分组覆盖 | 所有内容分组都关闭时，每列至少 3 个可用项（PRD F22） |
| 分组合法 | 每个 `tags` 值都在该模板的 `tagGroups` 中有定义 |
| 文本长度 | `note` ≤ 40 字，`notice` ≤ 60 字 |
| 黑名单词 | 内容中不出现 §10.3 中的词 |

### 9.2 人工抽查

1. 用脚本为每个模板随机生成 50 个完整组合（填入句式后的整句；有可选列的模板，开和关各抽 25 个；`couple` 在三档尺度下分别抽取）。
2. 逐条标记：✅ 合理 ／ ⚠️ 有点奇怪但能做 ／ ❌ 荒谬或无法执行。另对 `party` 和 `couple` 额外标记“尬”。
3. 合格线：❌ ≤ 2 条，⚠️ ≤ 5 条（§1.1）。
4. 不合格时，**优先修改或删除候选项**；只有内容修改无法解决时，才考虑互斥规则（PRD F21）。
5. 抽查结果记录在本文 §12。

## 10. 安全边界

### 10.1 全局红线（所有预设内容）

- 不涉及脱衣、裸露、性行为、隐私部位。
- 不涉及有明显身体风险的动作（高处、站上桌椅、靠近栏杆、危险物品）。公主抱、背着走这类常见互动允许，但需在须知中提醒安全。
- 不涉及金钱转账、损坏财物。
- 不含侮辱、攻击外貌或身材的内容。
- 不要求冒充他人、骚扰、恶作剧报警或其他会给场外的人造成麻烦的行为。
- 不出现博彩用语，不出现酒类或饮料品牌。

### 10.2 场景附加规则

| 场景 | 附加规则 |
|---|---|
| `party` | 熟人局标准【已确认】：身体接触不超过拥抱、牵手、捏肩、贴脸、喂食、弹脑门；不涉及亲吻和敏感部位。隐私只到感情经历、相册、屏幕使用时间这一级别，不涉及收入、健康、家庭矛盾。场外互动只针对熟人，内容无害。所有敏感内容必须打上对应 tag |
| `mix` | 有首次须知；结果提示“适量就好”；不放能量饮料；宣传不以“喝多”“灌醉”为卖点 |
| `couple` | 只限家中普通位置；最高档仍为 PG-13；“换一个”永远可用 |

### 10.3 黑名单词（用于自动检查）【建议，开发时补充完整】

脱、裸、性爱、床戏、胸、臀、私处、18+、成人、下注、中奖、Jackpot、手气、转账、灌醉、喝倒

### 10.4 用户控制手段

| 手段 | 作用 | 来源 |
|---|---|---|
| 换一个 | 跳过当前结果，不计次数 | PRD F06 |
| 排除 | 永久拿掉不喜欢的选项，可以恢复 | PRD F08 |
| 整组排除 | 一键关掉身体接触、隐私、场外互动、饮酒等整类内容 | PRD F22 |
| 尺度筛选 | 控制情侣互动的内容尺度 | PRD F09 |
| 可选列开关 | 情侣互动想加规则、调酒想兑两种饮料时打开 | PRD F10 |
| 首次须知 | 提醒双方自愿、未成年人勿饮酒 | PRD F17 |

### 10.5 用户自定义内容

- 用户在本地自定义模板中写的内容，由用户自己负责，产品不做审核。
- 通过短链接分享时：服务端只校验格式和大小，不审核内容；导入预览页**默认折叠选项内容**；违规内容由开发者按 ID 手动删除（PRD F15）。

## 11. 内容扩展机制

- **新增候选项**：在预设数据中追加，使用新的序号，不改动已有 ID。新增后必须重新完成 §9 的检查。
- **删除候选项**：删除后该序号作废，不再复用；用户偏好中引用的旧 ID 会被自动忽略（PRD F13）。
- **修改候选项**：修改 `label` 时，如果含义发生变化，应删除旧项并新增，而不是原地修改；只是措辞微调可以原地修改。
- **新增内容分组**：在模板的 `tagGroups` 中登记，并同步更新 PRD F22 的分组表。
- **新增预设模板**【未来】：同样遵守 §1 的原则和 §9 的检查，并在 PRD §4 中登记。
- **候选的未来场景**【未来】：外出吃什么、周末去哪、家务分工、学习任务。
