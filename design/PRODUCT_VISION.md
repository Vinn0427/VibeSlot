## 1. 一句话定义

**不知道干什么？转一下。**

EasySlot 是一个场景化的随机决策器：用户选择一个生活场景，转动多列老虎机，得到一个有趣、可执行的行动建议。【已确认】

## 2. 核心价值判断

### 2.1 三种需求的分工

| 需求 | 在产品中的角色 | 说明 |
|---|---|---|
| 决策辅助 | **入口**：用户打开的理由 | 动机真实，但随机做不出最优决策，只能打破僵局 |
| 娱乐体验 | **核心**：用户愿意转第二次的原因 | 动画手感、停止瞬间的期待、结果的意外感 |
| 社交互动 | **传播**：产品被别人看到的途径 | 约会、聚会场景天然带着“给对方看”的动作 |

【建议】三者不等权。资源冲突时的优先级：**娱乐体验（手感） > 内容质量 > 社交传播 > 决策精确度**。

### 2.2 关键洞察【假设】

用户使用随机决策器，主要不是为了得到最优解，而是为了：

1. **打破僵局**：“随便”“都行”的拉扯太累，需要一个外部力量做决定。
2. **转移责任**：结果是转出来的，不是我选的，双方都容易接受。
3. **暴露真实偏好**：转出结果后的第一反应（“好耶”或“不要”）就是真实偏好。
4. **制造仪式感**：把一个无聊的选择变成一个小游戏。

由此得出产品结论：

- **重转不是失败，是正常的使用方式。** 决策类场景默认不限次数，用户可以手动设置次数上限，作为自己选择的玩法规则（见 D17）。
- **锁定列 = 部分接受结果。** 这是用户逐步收敛到满意结果的核心工具。
- **内容质量决定结果是否“值得执行”。** 组合荒谬时，前面的手感全部白费。

### 2.3 真正的护城河

不是随机算法（随机没有门槛），而是：

1. **抽奖手感**：多列依次停止的节奏、反馈和动效。
2. **场景内容**：经过设计、任意组合都基本成立的候选项。
3. **多列组合**：相比单列转盘，组合带来更多意外感和可执行的具体信息。

## 3. 用户画像【假设】

| 画像 | 描述 | 典型诉求 | 对应场景 |
|---|---|---|---|
| 在家做饭的人 | 18–35 岁，独居或同居，经常自己做饭，买菜前不知道做什么、总做那几道菜 | 定下今天用什么食材，最好再告诉我做什么菜 | 今天做什么菜 |
| 情侣 | 恋爱中或已婚，周末和纪念日想找点新鲜事 | 打破“又是吃饭看电影”的循环；增加一些亲密小互动 | 约会、情侣互动（两个独立场景） |
| 聚会组织者 | 熟人局（老朋友、室友、同学）里负责活跃气氛的人 | 低门槛、不用准备、马上能玩，越玩越热闹 | 聚会挑战 |
| 小酌的年轻人 | 成年人，宿舍、出租屋或聚会前在便利店买酒，想喝点不一样的 | 用便利店就能买到的东西调一杯 | 便利店调酒 |
| 自定义型用户 | 有固定的选择清单（午饭轮换、周末计划、家务分工） | 把自己的清单变成老虎机，反复使用 | 自定义老虎机 |

## 4. 典型使用时刻

| 时刻 | 使用方式 | 人数与设备 |
|---|---|---|
| 下班买菜前 / 周末想做顿饭，不知道做什么 | 打开 → 转出“主料 × 配菜 × 风味” → 锁定主料 → 重转其余列 → 就它了 → 自己搜菜谱或去买菜 | 1–2 人，1 台手机 |
| 周六上午，情侣在沙发上不知道去哪 | 两人一起看转，转出约会的“原材料”（活动、吃什么、小彩蛋），轮流决定锁定哪一列 | 2 人，1 台手机 |
| 熟人聚会需要点气氛 | 手机放在桌子中间或轮流传，每轮一次挑战；不想玩的内容类型整组关掉 | 3–8 人，1 台手机围观 |
| 聚会前路过便利店 | 转出“基酒 × 饮料”（想丰富些就打开“再加一种”）→ 照着买 → 回去调 | 1–4 人，1 台手机 |
| 情侣晚上想增加一点小互动 | 设置尺度 → 转 → 执行或跳过 | 2 人，1 台手机 |
| 自己做了一个“周末计划”老虎机 | 发链接给朋友，朋友导入后也能转 | 跨设备分享 |

【已确认】V0.1 的“多人互动”指**单设备围观/传递**，不做在线同步。

## 5. 核心用户需求

1. **3 秒内开始转**：打开即用，无需登录，无需配置。
2. **结果能用**：不只是几个词，而是一个大致能执行的建议。
3. **能讨价还价**：不满意可以重转，满意的部分可以留下。
4. **能避开不想要的**：可以排除不喜欢的候选项，可以控制尺度。
5. **好玩**：转动过程本身有期待感。
6. **能拿给别人看**：结果和模板都能分享。
7. **能做自己的**：用自己的清单做一个老虎机，并保存下来。

---

## 6. 价值主张

> 把“选择困难”变成一个 3 秒钟的小游戏：转一下，得到一个能执行的主意；不满意就锁住喜欢的部分再转。

| 面向 | 价值 |
|---|---|
| 单人 | 替你做决定，省掉纠结 |
| 双人 | 避免“随便/都行”的拉扯，让结果显得“是命运的安排” |
| 多人 | 零准备的气氛道具 |
| 长期 | 自己的清单可以保存、复用、分享 |

## 7. 差异化

【假设】市面上存在大量单列转盘和“今天吃什么/做什么菜”类工具。EasySlot 的差异在于：

| 维度 | 常见转盘工具 | EasySlot |
|---|---|---|
| 结构 | 单列 | 多列组合，结果更具体、更意外 |
| 收敛方式 | 不满意只能全部重转 | 锁定列，逐步收敛 |
| 内容 | 用户自己填，或很粗糙 | 场景化预设内容，经过组合合理性设计 |
| 结果 | 一个词 | 组合 + 一句可执行建议 |
| 体验 | 工具感 | 强调动画手感与视觉趣味 |
| 分享 | 少见 | 结果分享 + 模板链接分享 |

以上对比基于常识性观察，未做系统的竞品调研，不作为市场结论。

## 9. 产品原则

所有文档和实现都必须遵守以下原则：

1. **随机列只放用户无所谓的维度。** 用户有明确偏好的维度（预算、距离、强度/尺度）不做成随机列，而是做成转动前的筛选条件或候选项元数据。【已确认】
2. **重转不设硬性门槛。** 不弹确认框，不惩罚；次数上限由用户手动设置，决策类场景默认不限。涉及互动/惩罚的内容，“跳过”永远可用且不计入次数。（见 D17）
3. **首次使用 3 秒内开始转。** 首页 → 选场景 → 转，中间不插入任何配置步骤。
4. **笛卡尔积中绝大多数组合必须合理。** 属性列的划分以此为首要标准：预设模板的列要彼此独立，靠内容设计避免矛盾，而不是靠规则修补。【已确认】
5. **有趣优先，但不越界。** 预设内容不含露骨成人内容；敏感内容（身体接触、隐私、场外互动、饮酒）打上分组标签，可以整组排除；所有挑战可以跳过；情侣互动另有尺度筛选。【已确认】
6. **像游戏，不像赌博。** 保留老虎机的交互隐喻，视觉上避免金币、777、Jackpot、下注、筹码等博彩元素。
7. **为围观设计。** 结果字号足够大、对比度足够高，几个人同看一台手机也能看清。
8. **轻量优先。** 无账号，数据保存在浏览器本地；后端只用于模板短链接这一件事；统计行为尽可能少。【已确认】
9. **内容自己说清楚。** 候选项只有一个短标签，不配说明文字；看不懂的选项应该改写，而不是加注释。【已确认】

## 10. 产品不是什么

- 不是推荐引擎：不根据位置、商家、历史行为推荐。
- 不是博彩或抽奖营销工具：没有奖品、积分、充值。
- 不是成人内容平台：预设内容最高到 PG-13 级别。
- 不是社区：没有公开浏览、搜索、评论；模板只通过短链接点对点传递（服务端仅保存被分享的模板数据）。
- 不是 AI 产品：V0.1 不依赖任何大模型。

## 11. V0.1 验证目标

### 11.1 要验证的假设

| # | 假设 | 验证方式 |
|---|---|---|
| H1 | 用户觉得转动过程好玩，会主动多转几次 | 每次进入老虎机页的平均转动次数 |
| H2 | 锁定列是有价值的收敛方式 | 有锁定行为的会话占比 |
| H3 | 结果足够可执行，用户愿意采纳 | “就它了”点击率 |
| H4 | 用户愿意分享结果或模板 | 分享点击率、模板链接打开数 |
| H5 | 有用户愿意做自己的老虎机 | 创建自定义模板的人数 |
| H6 | 用户会回来再用 | 回访会话占比（通过本地标记判断，不识别个人） |

### 11.2 统计原则【已确认：尽量轻】

- 只统计验证上述假设必需的少量事件（具体事件清单见 PRD / TECH_DESIGN，原则上不超过 8 个）。
- 不收集任何个人信息，不上报候选项和结果的具体内容，不使用跨站追踪 Cookie。
- 统计服务不可用时，产品功能完全不受影响。

### 11.3 参考目标值【建议，待上线后校准】

| 指标 | 参考值 |
|---|---|
| 每次进入老虎机页的平均转动次数 | ≥ 2 |
| 使用锁定的会话占比 | ≥ 20% |
| “就它了”点击率（以进入老虎机页的会话计） | ≥ 30% |
| 分享（结果或模板）的会话占比 | ≥ 5% |

这些数值是拍脑袋的起点，仅用于判断“明显好”或“明显差”，不是 KPI。

## 12. 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 组合荒谬、不可执行 | 用户觉得没用，转一次就走 | 正交内容设计 + 组合抽查（见 CONTENT_DESIGN） |
| 手感一般 | 失去核心差异 | 动画单独作为开发任务打磨（见 IMPLEMENTATION_PLAN） |
| 分享链接在微信中被拦截或打开慢 | 传播受阻 | V0.1 先用海外静态托管 + 自有域名做小范围验证；有起色后再备案并迁移到国内托管【已确认】 |
| 有人通过短链接传播违规内容 | 自有域名被举报或封禁 | 没有公开浏览入口；服务端校验大小和格式；开发者可按 ID 删除 |
| 互动/惩罚内容引起不适 | 口碑和平台风险 | PG-13 上限；聚会定位熟人局，敏感内容可整组排除；情侣互动有尺度筛选；聚会中的饮酒类默认排除；随时跳过 |
| 饮酒主题内容 | 未成年人使用、劝酒观感、平台对酒类内容的限制 | `mix` 首次须知（未成年人勿饮、喝酒不开车）；结果提示理性饮酒；不出现酒品牌；宣传不以“喝多”为卖点 |
| 博彩联想 | 平台审核与观感 | 视觉和文案规避博彩元素 |
| 自定义编辑在手机上太麻烦 | 自定义功能没人用 | 提供“从预设复制”，编辑器只保留最少字段 |

## 13. 长期演进方向【未来】

按“先验证，再加”的原则，以下方向只有在 V0.1 数据支持时才考虑：

| 阶段 | 方向 | 触发条件 |
|---|---|---|
| V0.2 | 简单音效与振动（已确认推迟到 V0.2）、分享图片卡片、聚会玩家名字、最近结果、简单权重（常出/普通/少出） | V0.1 核心指标达标 |
| V0.2–V0.3 | **AI 根据食材推荐菜品**：基于“今天做什么菜”转出的食材组合生成 1–3 道菜和简要做法（需要轻量后端或 Serverless 代理来保护 API Key） | 做菜场景的使用量和“就它了”率证明食材场景有价值；结合用户反馈判断 |
| V0.3 | 更多预设场景（周末去哪、外出吃什么、家务分工等）、组合互斥规则在编辑器中开放、冰箱清单（快速勾选“家里有的食材”） | 用户反馈有明确需求 |
| 更远 | LLM 将其他场景的组合扩写为具体方案；模板广场；双人异地同步转动；国内备案部署与小程序 | 有明确的用户规模和留存 |
